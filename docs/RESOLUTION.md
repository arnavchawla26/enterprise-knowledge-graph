# Entity resolution (ekg.resolve)

Numbers from `reports/resolution_metrics.json`, measured 2026-10-17 on the Project 1
enterprise (335 CRM account rows for 239 companies; 359,101 ERP assets for 359,101 real
drives).

## Accounts

Candidate pairs come from a block (same region, same first three letters of the
normalized name): 465 pairs out of 55,945 possible. Each is scored
`0.45 jaro_winkler + 0.30 token_overlap + 0.15 same_industry + 0.10 same_region`;
`>= 0.85` merges, `[0.70, 0.85)` goes to `reports/uncertain_matches.csv`, below is a
non-match. Rows sharing an `account_id` are joined by a separate rule and reported
separately, because an id join is not matching.

Companies are split 50/50 by a hash of the true canonical id; thresholds were set on the
dev half. Pairwise metrics on the held-out half (175 records, 129 companies, 69 true pairs):

| Matcher | Precision | Recall | F1 | Uncertain pairs (whole table) |
|---|---:|---:|---:|---:|
| Name + industry + region (shipped) | 1.000 | 1.000 | 1.000 | 24 (1 is a true pair) |
| Name only (ablation, no industry/region weight) | 1.000 | 1.000 | 1.000 | 295 |
| Shipped + same-id rule | 1.000 | 1.000 | 1.000 | 24 |

Canonical-id accuracy (the cluster's chosen id equals the truth id): 1.000 on both halves.

What this proves and does not. The mess was generated by rules A1 to A3 in Project 1's
`docs/MESS_RULES.md`: three spellings with a fixed set of edits, duplicate ids, duplicate
rows, and every variant keeps the company's region and industry. A perfect score says the
matcher inverts those rules on companies it was not tuned on; it says nothing about a real
CRM, where variants change region, share names across subsidiaries, and carry typos in the
first word (which would defeat the block). The honest number is the review list: with
industry and region as evidence, a reviewer looks at 24 pairs; with names alone, 295. The
site/contact-overlap feature exists in the code but carries no weight, because in this data
no site or contact ever cites a duplicate id (`duplicate_ids_cited_by_sites: 0`).

Top of the review list (`reports/uncertain_matches.csv`): "Maplewood Anal. plc" vs
"Maplewood Anlytcs plc" (0.82, a true pair the thresholds miss on its own; it merges through
the canonical spelling), then different companies that share a first word and a region:
"Cedarbrook Mutual plc" vs "Cedarbrook Retail Holdings" (0.82), "Lakeshore Health Holdings"
vs "Lakeshore Mutual Holdings" (0.81).

## Assets

The ERP serial is the telemetry serial with, in 18% of rows, a vendor prefix (rule S1) or
lowercase (rule S2). The first version of the matcher stripped prefixes and upper-cased
blindly and lost 505 assets: 430 real telemetry serials are natively lowercase and 86
genuinely start with `WD-`. The shipped matcher tries candidates in order (raw, prefix
stripped, upper-cased, both) against the set of known telemetry serials and takes the
first hit, scored 1.0 / 0.95 / 0.95 / 0.9; a serial already claimed is a collision and is
reported, not linked.

| | Assets | Matched | Correct | Precision | Recall | Collisions |
|---|---:|---:|---:|---:|---:|---:|
| All | 359,101 | 359,101 | 359,101 | 1.000 | 1.000 | 0 |
| Held-out half (by asset-id hash) | 179,302 | 179,302 | 179,302 | | 1.000 | |

By method: 295,955 exact, 53,899 prefix stripped, 9,247 upper-cased. By mess type the
rule inverts all of `none` (295,948), `vendor_prefix` (53,899) and `lowercase` (9,254).

This is a rule checked against data, not a learned matcher; the number proves the rule
inverts S1 and S2 without breaking real serials. It would not survive a real ERP where
serials are re-keyed or truncated.
